{{- if not .Values.secrets.existingSecret }}
{{- if not .Values.secrets.authSecret }}

WARNING: secrets.authSecret is unset.

TEAMUP_AUTH_SECRET wraps the JWT signing key that TeamUp persists in the
database. Set it now, before anyone signs in:

  secrets:
    authSecret: "$(openssl rand -base64 48)"
{{- end }}
{{- end }}

Two things about TEAMUP_AUTH_SECRET that are easy to learn the hard way:

  * Lose it, and every issued session and refresh token stops verifying.
    Everybody is logged out and cannot be logged back in with old tokens.
    Back it up wherever you keep your other break-glass secrets.
  * Change it, and the same thing happens — it is not a rotation you can do
    casually. Every replica must carry the identical value, which is why it
    lives in one Secret rather than being generated per pod.

{{- $wanted := int .Values.replicaCount }}
{{- if .Values.autoscaling.enabled }}{{ $wanted = int .Values.autoscaling.maxReplicas }}{{ end }}
{{- if gt $wanted 1 }}

Running {{ $wanted }} replicas. They share their state through Redis:

  * Every replica publishes each broadcast onto a Redis pub/sub channel and
    subscribes to it, so a message, a call and a presence change reach every
    session in the deployment — not only the share on the pod that sent it.
  * Whether somebody is connected is counted across all of them, so a person
    with a laptop on one pod and a phone on another shows online until both
    have gone.
  * No sticky sessions needed. A client may reconnect to any pod.

All of that runs over TEAMUP_REDIS_URL. Point every replica at the same Redis
or they will not see each other, and check that they can:

  teamup_ws_fanout_subscribed
      1 while a pod is receiving. 0 on a running pod means it is deaf to the
      others, which from the outside looks like nothing at all. Alert on it.

  teamup_ws_fanout_resubscribes_total
      Rises when a pod loses Redis and gets it back. Each one closes that pod's
      sessions so its clients reconnect and refetch — pub/sub cannot replay
      what was missed, so there is no honest alternative.

  teamup_ws_fanout_dropped_total
      Anything but zero is messages that did not cross between replicas. The
      reason label says whether that was Redis or this pod.
{{- else }}

Running a single replica. It works, and messages, calls and presence are all
correct — but every `helm upgrade`, node drain or crash disconnects everybody
at once, because there is no second pod to serve them meanwhile.

Two replicas is the smallest configuration that survives a rollout. They share
their state over the Redis you already run; see replicaCount in values.yaml.
{{- end }}

Every replica must carry the identical TEAMUP_AUTH_SECRET — which they do,
since they read the one Secret above.

Health endpoints:

  /healthz  liveness  — the process is up
  /readyz   readiness — PostgreSQL, Redis, object storage and, when
                        TEAMUP_LIVEKIT_URL names an HTTP endpoint, LiveKit

A pod that cannot reach one of those stays out of the Service until it can,
rather than answering 500 to uploads and calls behind a rollout that looks
green.
